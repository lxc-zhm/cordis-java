# 订单、库存、支付与仓配示例

这里运行一个多租户电商结算流程。每笔订单会校验商品、预占库存、获取沙箱支付回执、更新支付状态，并生成仓配出库单。
数据写入本地 YAML 快照；所有插件卸载并重新打开后，订单、库存、支付和出库记录仍能恢复。

## 运行

在仓库根目录执行：

```sh
mvn test
mvn install
mvn -pl cordis-example exec:java
# 指定数据目录，便于运行后查看或再次打开；相同演示请求键会复用原订单
mvn -pl cordis-example exec:java -Dexec.args="/tmp/my-commerce-demo"
```

默认创建一个新的临时数据目录，结束时打印其路径。`shop-a.yaml` 和 `shop-b.yaml` 是独立店铺的数据，
旁边的 `.lock` 文件用于阻止两个数据库会话同时覆盖同一份数据。

输出是已经执行并校验过的业务结果，例如：

```text
首次下单：PAID，原价 ¥136.00，优惠 ¥0.00，实付 ¥136.00。
重复提交：返回同一订单，未重复扣库存或扣款。
支付拒绝：订单记录为 PAYMENT_FAILED，库存已释放，没有支付或出库凭证。
会员促销上线后的新订单：PAID，原价 ¥136.00，优惠 ¥13.60，实付 ¥122.40。
```

## 插件职责

| 插件 | 业务职责 | Cordis 机制的实际作用 |
|---|---|---|
| DatabasePlugin | 管理租户数据文件和独占文件锁 | 用 effect 管理会话，卸载释放锁，不删除业务数据 |
| InventoryPlugin | 商品目录、库存预占和释放 | 依赖数据库，库存和订单状态在同一事务内变更 |
| PaymentPlugin | 沙箱扣款、支付幂等和退款凭证 | 停用后依赖它的结算自动进入 PENDING |
| StandardPricingPlugin / MemberPricingPlugin | 原价结算、金卡满额优惠 | 热替换促销策略，或按配置修改折扣；历史报价保持不变 |
| OrderPlugin | 下单编排、重复请求识别、支付失败补偿、取消订单 | 依赖库存、支付与定价；卸载使旧服务引用拒绝新业务写入 |
| OrderQueryPlugin | 历史订单查询 | 只依赖数据库，支付维护和促销更新不影响查询 |
| FulfillmentPlugin | 消费订单 outbox，幂等生成出库单 | 事件监听随插件移除；重新启用时补处理积压任务 |

入口是 `Main`，组合和运营操作在 `CommerceApplication`，业务规则在 `service`，不可变领域数据在
`domain/Commerce.java`，本地持久化适配器在 `persistence/CommerceDatabase.java`。
插件的 `apply` 只负责组装服务、声明依赖、登记资源和订阅业务事件。

## 可以观察到的业务行为

1. **下单与幂等**：数量校验、商品查询、合并重复 SKU、库存预占、金额计算、支付回执、出库单。
   相同请求键和内容返回原订单；相同键提交不同内容会拒绝。金额使用整数分，折扣按四舍五入计算。
2. **失败补偿**：购物车任一商品库存不足，整笔预占事务不提交；支付拒绝则保留失败订单并释放库存。
   已扣款但尚未提交 PAID 状态的订单，在下一次激活时通过原支付回执恢复，不重复扣款。
3. **取消与退款**：已支付但未出库的订单可以取消，退款、库存释放和 outbox 撤除只执行一次。
   已经出库的订单要求走售后流程，不能直接恢复库存。
4. **维护降级**：支付插件停用时，结算服务不可用，查询服务继续工作；恢复支付后重新激活结算。
5. **仓配补处理**：停用仓配后仍可付款，出库任务保留在 outbox；恢复时创建缺失的出库单。
   PAID 状态与 outbox 在同一次提交中写入，出库单与任务完成标记也在同一次提交中写入。
6. **审计权限**：订单服务通过调用者上下文视图解释 `readOnly`，审计角色可查询，不能下单或退款。
7. **租户隔离**：两个店铺可使用相同 SKU 和请求键，但价格、库存、订单、支付和仓配事件互不串用。
8. **促销发布**：从原价策略热替换到金卡优惠策略，新订单获得满 100 元减 10% 的优惠，旧订单金额不变。
   集成测试还验证了失败发布恢复上一版策略，以及配置修改为 15% 后的新订单报价。

## 数据与适配器边界

这是有业务规则、事务和落盘行为的可运行示例。支付通道和仓配系统是明确的本地沙箱适配器，
只支持 `test-card` / `declined`，不会访问真实支付、短信或物流接口。
文件存储使用进程内事务与原子快照替换，便于直接观察和测试；它不代替生产数据库的索引、迁移、
备份与故障恢复能力。沙箱支付/退款记录与订单共用本地存储；对接真实外部网关时，需要其幂等接口、
回调验签、对账和分布式失败恢复，不能把本例的本地事务视为跨系统原子事务。

框架撤销的是连接、服务注册和事件监听等运行资源。订单和已发生的支付不应因为插件卸载而被“撤销”；
业务补偿由明确的状态转换和退款规则负责。

`CommerceWorkflowTest` 的 16 个集成测试验证业务结果，包括并发重复请求、整单库存回退、
支付维护时持续查询、租户事件隔离、真实文件重开，以及扣款后中断的恢复。
